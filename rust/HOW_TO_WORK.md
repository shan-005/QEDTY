# HOW TO WORK — QEDTY Rust developer guide

This file is the execution manual for developers working on the Rust implementation.

## 0. Rules before editing

1. Work against the current QEDTY repository—not a reconstructed tree or an imported scaffold treated as authoritative.
2. Keep `crates/qedty-core/` as the one canonical native implementation unless an approved architecture decision explicitly migrates it.
3. Do not change Python semantics, IDs, canonical JSON, contract schemas, or golden expected outputs just to make Rust tests pass.
4. Treat `data/contracts/golden-vectors/` as shared, versioned test fixtures. Changing expected results is a contract change and requires review.
5. Do not use `unwrap()`/`expect()` on externally controlled input in production paths. Tests may use them with meaningful context.
6. Avoid nondeterministic iteration/order in externally visible output. Document any accepted floating-point tolerance.
7. Do not add a dependency because it is fashionable. State what it does, why the standard library/current dependency set is insufficient, its license/MSRV implications, and the test that needs it.

## 1. Environment

Install Rust through the official rustup instructions. This repository pins the Rust development toolchain in root `rust-toolchain.toml` (Rust 1.99.0 as researched on 2026-10-09) with `rustfmt` and Clippy. The core crate retains its declared `rust-version = "1.78"`; the pinned developer toolchain is not a silent promise to raise the MSRV.

Confirm the toolchain from the repository root:

```bash
rustc --version
cargo --version
rustup show active-toolchain
```

## 2. First-run check

```bash
cargo metadata --locked --format-version 1 --no-deps
cargo test --workspace --locked
cargo run --locked -p qedty-conformance
```

The committed root lockfile should be regenerated by Cargo and reviewed when integrating this bundle if Cargo reports that it needs an update. Do not hand-edit checksums or choose versions by copying a blog post. After the generated lockfile is committed, CI must use `--locked`.

## 3. The required verification loop

For every Rust kernel change, run:

```bash
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo run --locked -p qedty-conformance
uv run python scripts/check_core_conformance.py
uv run pytest -q
```

When editing geometry, temporal, graph, propagation, or numerical algorithms, also run that domain's Python conformance checker and its golden-vector tests. The full Python test suite is a release gate, not an excuse to omit focused tests.

## 4. How one kernel is added

1. **Locate the reference implementation.** Identify the exact Python function, input model, errors, boundary semantics, units, and output shape.
2. **Read the existing contract and vector.** Prefer the shared vector location under `data/contracts/golden-vectors/<domain>/`. If no vector exists, add one from the Python implementation first and review its contract semantics.
3. **Define the Rust API.** Specify input types, validation, errors, deterministic guarantees, tolerance, and ownership/allocation behavior before optimizing.
4. **Implement a small, safe baseline.** Prefer clear safe Rust. Keep unsafe code absent unless performance evidence establishes a need and a safety review is added.
5. **Test in layers.** Unit tests for local edge cases; property tests for invariants; shared golden-vector tests for cross-language behavior; fuzz targets for parsers/complex input; differential tests against Python.
6. **Benchmark the baseline.** Record target, toolchain, CPU, workload size, warm-up, sample settings, and benchmark command. Avoid hard-coded universal throughput promises.
7. **Profile before optimizing.** Optimize the observed hotspot, not the most exciting algorithm.
8. **Integrate and review.** Run Python and Rust checks, update domain documentation, and include behavior changes and benchmark evidence in the PR.
9. **Expose through PyO3 only after stabilization.** Keep the current Python package/build backend intact until a dedicated packaging decision is approved.

## 5. How to run the shared-vector CLI

```bash
cargo run --locked -p qedty-conformance
```

It reads these existing files from the repository:

- `data/contracts/golden-vectors/core/canonical_json.json`
- `data/contracts/golden-vectors/core/identity.json`
- `data/contracts/golden-vectors/core/geometry_ecef.json`

It reports **only vectors implemented by the current Rust core API**. `quantity.json` and `time.json` are intentionally not reported as passing because there is not yet a corresponding Rust conversion/normalization API in the current core. Adding those capabilities requires reference semantics and tests first.

## 6. Error handling and numeric policy

- Use typed error enums for expected invalid input and conversion failures.
- Preserve existing API signatures during module decomposition; additive fallible methods are preferred over silently changing public behavior.
- Reject non-finite values wherever a domain contract forbids them. Do not silently coerce invalid latitude/longitude or timestamps.
- For floating-point kernels, document finite-value behavior, units, edge domains, and explicit tolerances. Exact bitwise equality is not assumed across hardware/math libraries unless specifically guaranteed.
- Do not use floating-point values as identity/hash inputs unless the contract fully specifies NaN, signed zero, serialization, and rounding behavior.
- For deterministic reductions, define ordering and tie-breaking explicitly.

## 7. Dependency and supply-chain changes

Before adding a crate:

- Record the need in the PR.
- Check the crate's supported Rust version and active maintenance.
- Check licenses and transitive dependency impact.
- Run `cargo tree -d` and inspect newly introduced transitive versions.
- Run `cargo deny check` when the repository's `deny.toml` and tool are adopted.
- Preserve the lockfile and use `--locked` in CI.

`proptest` is recommended for invariants, Criterion for statistical benchmarks, `cargo-fuzz` for fuzzing complex parsers/input paths, and `cargo-llvm-cov` for source-based coverage. Add them only to the specific crate that uses them. Fuzzing commonly needs nightly; keep that in an explicitly separate job from stable required CI.

## 8. Pull request template for a kernel change

A Rust kernel PR should state:

- Python reference function(s) and reference commit/version;
- shared contract/vector IDs;
- public API and error behavior;
- determinism and tolerance guarantees;
- unit/property/differential/fuzz tests run;
- benchmark command, machine/toolchain, workload, before/after measurements;
- memory/allocation observations;
- dependencies added and license/MSRV effects;
- Python integration behavior and any compatibility implications.

## 9. Scope boundaries

- Do not implement Go, CUDA, React, PostgreSQL production persistence, or WASM as part of the Rust implementation scope.
- Do not create twenty domain crates that contain only `lib.rs` placeholders.
- Do not replace setuptools with maturin as a side effect of the first Rust kernel.
- Do not claim performance wins from debug builds or single noisy timing samples.
- Do not describe an implementation as conformant because it compiles; vectors and differential tests must pass.
