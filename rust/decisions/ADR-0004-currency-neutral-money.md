# ADR-0004: Currency-neutral money and explicit FX snapshots

- **Status:** Proposed for v2 implementation review
- **Context:** The v1 optimization and protobuf contracts use USD-named floating-point fields. The existing `Money` helper does not bind amounts to versioned currency precision or an explicit FX input. Reinterpreting those v1 fields would silently break compatibility.
- **Decision:** Add a separate v2 monetary boundary based on Python `Decimal`, caller-supplied currency metadata profiles, and immutable FX snapshots. Keep v1 models, fields, and semantics unchanged. Currency metadata is data-driven; the kernel does not contain a currency allowlist.
- **Amount representation:** A monetary amount is a finite non-negative decimal, a three-uppercase-letter currency code, and a metadata-profile version. Floats are rejected at the Python boundary. A profile states each code's minor-unit scale and one supported decimal rounding mode. Input amounts that cannot be represented at the declared scale are rejected rather than silently rounded.
- **FX semantics:** A rate is quote-currency units per one base-currency unit. A snapshot carries an ID, as-of timestamp, validity interval, and rates with observation time, source, and provenance ID. Conversion accepts an explicit snapshot for cross-currency requests; it never fetches rates. One quoted pair is permitted per unordered currency pair. A direct quote is used as supplied; if only the reverse quote exists, its reciprocal is used with 34 significant decimal digits and half-even arithmetic. Triangulation is deliberately disabled in this version, so missing direct/reverse quotes fail explicitly. Spreads and fees are not inferred.
- **Rounding:** Conversion multiplies at 34 significant decimal digits using half-even arithmetic, then rounds exactly once to the target currency's declared minor-unit scale using that target profile's rounding mode. Same-currency conversion does not require an FX snapshot.
- **Validity and errors:** Timestamps must be timezone-aware and are normalized to UTC. An FX snapshot is usable only inside its half-open validity interval `[valid_from, valid_to)`. Missing metadata, profile-version mismatches, excess input precision, stale snapshots, missing quotes, invalid rates, or invalid monetary values fail explicitly.
- **Alternatives rejected:** Reinterpreting v1 `*_usd` fields; accepting binary floats for money; implicit online FX lookup; implicit FX triangulation; hard-coded supported-currency lists.
- **Canonical result text:** All non-monetary decimal values emitted by the v2 optimizer use fixed-point base-10 strings with redundant fractional zeroes removed and signed zero normalized to `0`. Monetary amounts retain their currency-scale representation. This avoids binary floats and gives Python/Rust exact text parity.
- **Consequences:** This establishes the auditable money/FX substrate only. It does **not** by itself establish full portfolio-optimizer parity or Rust parity. The next contract must build the v2 portfolio request/result and solver status on this substrate, then add Python reference tests and a matched Rust adapter.
- **Compatibility risks:** Decimal arithmetic and explicit profiles intentionally differ from the existing float-based v1 helpers. V1 remains supported without reinterpretation.
- **Test evidence required:** Schema self-validation; direct and reciprocal conversion; rounding mode and target scale; metadata/profile mismatch; malformed/non-finite/negative values; stale and invalid timestamps; missing quotes; disabled triangulation; and fixed independent Python–Rust cases before claiming native parity.
- **Revisit when:** A reviewed v2 portfolio contract requires a different rate-path, fee, or monetary-arithmetic policy. Such changes must be versioned rather than silently altering this contract.
